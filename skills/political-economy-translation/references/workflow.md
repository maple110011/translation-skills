# 长文与批量：断点续译

默认流程是**整篇读入、逐段输出**（见 SKILL 第 3 步）：上下文装得下全文，分几次写只是输出上限的问题，中间不需要"块"这个概念。

这份文档管另外两种情况：

- **真的超出窗口**——少见，通常是长篇综述或附录极多的文章；这时才需要把原文切成片段分别读。
- **需要跨会话续译**——一次对话写不完、中途要回去改、一批文献排队处理。

这两种情况下"段"变成需要外部记录的东西：写到哪、还剩什么、术语和风格怎么恢复。下面讲的就是这个。

---

## 一、开工前：分段清单

不要边读边切。先出一份分段清单，落成文件，后面每一步都对着它走。**窗口内翻译也值得跑一遍**——清单告诉你每段有多大，据此定输出段界（2000–4000 汉字一段）。

```bash
# 用二级标题切，块过大再按段落切
python - <<'EOF'
import re, json, os
src = open('paper_原文.md', encoding='utf-8').read()
parts, cur, cur_title = [], [], None
for line in src.split('\n'):
    if re.match(r'^##\s', line) and cur:
        parts.append((cur_title, '\n'.join(cur)))
        cur, cur_title = [line], line
    else:
        if cur_title is None:
            cur_title = line
        cur.append(line)
if cur:
    parts.append((cur_title, '\n'.join(cur)))
manifest = [{'i': i + 1, 'title': t.strip(), 'chars': len(b),
             'paras': len([p for p in b.split('\n\n') if p.strip()])}
            for i, (t, b) in enumerate(parts)]
json.dump(manifest, open('_work/manifest.json', 'w'), ensure_ascii=False, indent=1)
for m in manifest:
    print(f"{m['i']:>2}. {m['chars']:>6} 字 {m['paras']:>3} 段  {m['title'][:50]}")
EOF
```

清单里记下每块的**字符数与段落数**。段落数是后面校验的基准，丢了就无从对账。

## 二、逐段译，逐段落盘

原则：**写完一段就追加进译文，不要攒在内存里。**

好处不是省事，是出错能定位：整篇写完才发现第 40 段丢了，得通读全文去找；逐段写的话，`fidelity_check.py` 会直接告诉你哪一块对不上。

每一段的流程固定：

1. 读这一段对应的原文。**窗口内翻译不回头读前文**——全文本来就在眼前，代词和语气模型自己接得住。只有真的切了原文（超窗口那种情况）才需要连同上一段最后三段一起读，那时模型看不见全文，衔接得靠补。
2. 数段落、列表项、公式块、表格。
3. 译。
4. 追加写入译文文件。
5. 在这一段末尾留一个 HTML 注释标记进度：

```markdown
<!-- chunk 7/23 done: 12 paras -->
```

注释不会被渲染，但对账时有锚点。全部完成后统一删掉（`fidelity_check.py` 不会把 HTML 注释算成块，所以留着也不影响，但交付前清掉更干净）。

## 三、断点恢复

新会话接手时，按顺序做：

1. 读 `_work/manifest.json`，知道总共几块。
2. 读 `paper_zh.md`，找最后一个 `<!-- chunk n/... -->` 标记，n 之后的就是待译。
3. 读 `_work/paper_术语.csv`，恢复术语约定。
4. 读 `_work/paper_风格.md`，恢复自称、论证动词口径、句式基调和样板段。
5. 读上一块译文的最后两段，恢复语气与代词指代。
6. 从第 n+1 块继续。

**不要凭记忆接着写。** 换了会话，术语和语气都会漂。这四份文件（manifest、术语表、风格约定、已译部分）就是记忆本身。

风格约定比术语表更容易被跳过，因为它不像"表"而像"说明"。跳过它的代价在后面才显形：续译的最初三块往往读着像换了个人，而且每一块单独看都合格，靠通读也难定位——只能靠下一节的抽查。

## 四、批量多文件

一批论文一起处理时，顺序很重要：

```
先全部提取 → 再统一术语 → 再逐篇翻译 → 最后逐篇对账
```

不要"提取一篇译一篇"。原因：术语必须在所有文章之间统一，先译完一篇会锁死一套译法，第二篇发现更好的写法时已经改不动了。

**多篇同时开工时，一篇交给一个子代理**（见 SKILL 第 0 步）：每篇独立一个 `_work/`、一份项目术语表、一条完整的第 1→6 步链路；主代理只派活、收活、核对产物。理由与任务说明的写法在 SKILL 那一节，这里只说一条纪律——**主代理不要顺手替子代理改正文**，改了就对不上它自己的对账记录，最后谁也不知道哪一版是真的。

批量术语统一的做法：

```bash
# 把所有项目的术语表并起来看冲突
python scripts/merge_glossary.py ./_work/*_术语.csv -o ./_work/merged
# 裁决后生成一份共同表，各篇引用同一份
```

## 五、什么时候该停下来问人

这四种情况不要自己决定：

- **原文自相矛盾且影响结论。** 第 3 节说某量下降，第 5 节的数据表显示上升。照译、记录，交给用户判断。
- **术语在本文语境下有两种截然不同的译法，且都会改变论证。** 例如 `determines` 在一处是"决定"、另一处若译"制约"会让因果方向反过来。
- **提取质量不可用。** 整篇双栏串行、公式全成图片、脚注全丢。这时候继续译是在浪费双方时间。
- **选词本身即立场。** `surplus approach` 译"剩余方法"还是"剩余进路"，等于替用户选了他在学界的位置。这类不要替用户选。

### 记下来，别攒到最后

开工前建一份人工待校表，遇到就写一行：

```bash
python scripts/review_queue.py --init-manual _work/x_人工待校.csv
```

列是 `位置,类型,原文,译法A,译法B,建议,理由`。**不要等全部译完再回想**——到那时，前二十页的判断已经被后面的内容覆盖，只剩"好像有个地方不太对"的模糊印象。

交付前合并成清单：

```bash
python scripts/review_queue.py 原文.md 译文.md --glossary _work/x_术语.csv \
    --manual _work/x_人工待校.csv -o _work/x_待校对.md
```

脚本自己会查出三类：术语在原文出现但译文没用约定写法、术语表里标着待定的条目、原文中反复出现却未收录的新术语。剩下四类——歧义、术语未定、学派立场、原文疑误——只在你手写的那份里，脚本不会替你判断。

批处理多个文件时，每个文件单独一份待校表，不要合并：一个术语在两篇里可能需要不同处理，合在一起反而看不出是哪篇的问题。

## 六、进度与质量的取舍

长文最容易出的事不是译错，是**后三分之一明显变糙**：句子变短、连接词变少、术语开始漂、长句直接照搬英文语序。

对策是强制节奏，不是靠自觉：

- 每译完 5 段，回头抽查第 1 段与刚译完的这段，比较术语与句式密度。全文在窗口里不等于注意力不衰减——这恰恰是"后三分之一变糙"的来源。
- 每 10 段跑一次 `fidelity_check.py`（对已完成部分），不要等到最后。
- 单次会话不要连续输出超过 8 段。宁可分两次，也不要写到注意力耗尽。

判断"变糙"的具体指标：一个段落里"的"出现超过 6 次；连续三句以"这""该""其"开头；出现"进行了……的分析""对……加以……"这类结构；术语与项目表不一致。
