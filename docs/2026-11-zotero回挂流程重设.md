## 一句话

旧流程不是"自动化没做好"，而是**一次都没真正执行过**。根因不是缺 API key，是把唯一的自动通路绑在了错误的前置条件上。

---

## 一、旧方案的实测结论

### 环境事实（本机，2026-11-14）

| 项 | 实测 | 意味着 |
|---|---|---|
| Zotero 版本 | **10.0.8** | 本地 API 支持写入与文件上传（10+ 才有） |
| 本地 API | `GET 127.0.0.1:23119/api/users/0/items` → 200 | 免认证可读 |
| 本地写 | `POST /items` → 401，提示 `POST /api/local/authorize` | 只差一次弹窗授权，**不是缺 zotero.org 账号** |
| `pyzotero` | 未安装 | 旧脚本的"自动"分支在本机永远是死的 |
| `ZOTERO_API_KEY` | 未配置 | 同上 |

### 产物事实

三篇交付稿的 `_work/zotero_attach.json` 全是 `status: prepared`、`parent_key: null`、`reason: 未配置 ZOTERO_API_KEY`。

而用本地只读 API 按 `title_en` 各搜一次，**三篇一次全中**：`GAS4E39W` / `BM3PDSX9` / `U28WLFMK`。

**锚定从来不是难点，是脚本没去问。**

## 二、旧方案的问题

### P0

1. **最强的通路没用上。** 本地 API 读免认证、写只需一次授权、文件上传三步本地全支持，且不需要任何第三方库。旧实现只认 Web API，把唯一的零成本自动化路径锁死。
2. **零配置路径不做锚定。** `prepare()` 里根本没有"查父条目"的动作，`parent_key` 恒为 null，也就没有 `zotero://select` 链接。用户得自己在几千条文献里翻出那条再右键挂附件——成本比翻译一段还高，所以没人做。
3. **citekey 冒充 DOI。** 实测样例：`"doi": "hollmann2022tabpfn-zh"`，这是译文 citekey。真配上 key 那天，这条会拿无效标识去搜。
4. **同名附件即跳过。** 判据只有 `filename`，一旦存在就 `already-attached`。改稿重出的 PDF 被静默丢弃，且与文档里"重跑会生成新版本"的说法矛盾。

### P1

- manifest 写在 `pdf.parent/_work/`，多篇 PDF 放同一目录会互相覆盖；
- 待挂副本逐篇分散（三篇三处，重复 2.1 MB）；
- Zotero 步骤不在第 6 步产出表里，模型不会当步骤执行；
- 无批量入口；`drag_title()` 对 `<stem>_zh.pdf` 恒失效。

### P2

- **编排不一致**：政经 SKILL.md 的 `</workflow>` 在第 566 行闭合，回挂 Zotero 从第 568 行开始——**在流程块之外**，等于附录；dl 的在块内。同一段文字，一份是步骤，一份是脚注。
- DOI 搜索走 `q` 默认域（title + creator），DOI 未必命中；
- 幂等只看文件名，不看内容。

## 三、被否掉的替代方案

| 方案 | 否掉的原因 |
|---|---|
| 继续用 zotero.org Web API + `pyzotero` | 多一个账号、一个 key、一个依赖、一次联网；能力上并不比本地 API 多 |
| 直接写 `zotero.sqlite` | 运行时数据库被锁，手工插 item 会破坏同步，也可能损坏整个库 |
| 直接往 `storage/<KEY>/` 放文件 | 没有 DB 记录，Zotero UI 里不会出现；等于自造一套半成品 |
| 只生成"待挂副本 + 手动拖拽" | 实测三篇全停在这一步，说明人工成本已经超过阈值。降级路径要能批量，不能逐篇 |

## 四、采纳的设计

**本地 API 优先，手工兜底，一路可重跑。** 细节在 `references/zotero.md`，这里只记四条决定：

1. **锚定先于上传。** 锚不到就不产出副本——没有目标的副本是垃圾。顺序：`--parent-key` > DOI/arXiv 等值 > `source_pdf` 与库里附件 filename 精确相等 > 英文标题唯一命中。
2. **判重用 filename + md5，改稿原地覆盖。** 覆盖时复用同一个附件条目，附件数不变。
3. **降级不再复制副本**，改为 `_zotero/pending.md` + 可粘进 Zotero 运行器的 `attach.js`。Zotero 自己导入时会把文件复制进 `storage/`，中间副本纯冗余。
4. **独立成第 7 步，放进 `<workflow>` 块内**，并在交付回复模板里报挂载状态。理由见 §二 P2：块外的步骤等于不存在。

### 实测踩到的三处实现差异（Zotero 10.0.8）

官方文档按 Web API 语义写，本地实现不完全照做。这三条已写进脚本注释：

| 差异 | 文档说法 | 实际 |
|---|---|---|
| 上传参数位置 | query string | **必须放 form body**，query 传直接 500 空响应 |
| 覆盖时 `If-Match` | 「`If-Match` 或 `If-None-Match` 头」 | 值**必须是旧文件 md5**（文件 ETag），传条目 version → 400 |
| 主机名 | `localhost:23119` | 用 **`127.0.0.1`**；Windows 上 `localhost` 先试 `::1` 再回退，每请求多 2 秒 |

另：全量拉 `GET /items?itemType=attachment` 会超时（本机 3285 条），锚定改用 quicksearch 反查，不建全量索引。

文件落盘到 Zotero 数据目录下的 `storage/<附件KEY>/zh - <原文附件名>.pdf`。数据目录不一定是默认位置，脚本本身不依赖这个路径。

验收：

| 场景 | 结果 |
|---|---|
| 批量首挂 | 3/3 `attached`，rc=0 |
| 原样重跑 | 3/3 `unchanged`，库里不出现第二份 |
| 改一版 PDF 重跑 | `updated`，同一附件被替换，附件数不变，md5 对齐 |
| 锚定失败 | `pending` rc=2；`--strict` rc=1 |
| 上传中途失败 | 空壳附件已回滚（调试期三次 500/400 都删净） |
